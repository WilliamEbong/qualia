# Requirements analysis

Nine requirements and four success criteria map to ten tasks; coverage 100%.

- Principle I: both new tables are append-only with SQLite triggers created by migration 003; decisions reference proposals; accepting writes a draft `codes` change (mutable by design) plus an immutable decision recording exactly what was applied.
- Principle II: no automated path edits codes. Evidence and AI paths only insert proposals; only `decide_code_proposal`, called with a human actor from the API/CLI, changes the draft. Frozen versions and METHODOLOGY.md are untouched; freezing stays a separate human action.
- Principle III: proposals never read benchmarks, validation predictions or the vault; the miner uses review decisions and current codings only. No metric changes.
- Principle IV: vendor launches stay in claude_cli.py and codex_cli.py with the existing no-tools, empty-directory transport; the proposal output passes a strict pydantic adapter that names the failing record. The miner lives in sealed `qualia/core`.
- Principle V: AI proposals pass `allow_external`, availability, budget and egress gates through `ledger.reserve`; evidence mode is offline. The demo stays read-only.
- Principle VI/VII: no data or secrets; no dependency; tests land with code.
- Technology: the prompt is an in-code constant, so `pipeline_hash` and the improvement loop's mutable scope do not change; OpenAPI regenerated by the main session.

Risks: provider structured-output rules (all properties required) — the schema marks every field required; long Claude outputs — bounded to 12 proposals and existing `max_output_tokens`; a stale target (code archived after proposal) — acceptance still applies to the draft and the person sees the current code in the editor. No CRITICAL issue.
