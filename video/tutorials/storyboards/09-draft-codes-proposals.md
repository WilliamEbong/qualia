# Draft and refine codes through proposals

Guide sections: 6 (proposals)
Target length: 3–4 min
Starting state: practice-study after coded

Recording note: Use the section 3 practice snapshot; proposal generation uses `fake` throughout, with names and IDs taken from the returned cards.

1. Select `Codebook`, then expand `Ask for proposals` under `Proposals`. — "A proposal changes nothing until you accept it into the draft codebook."
2. [demo] Set `Proposal type` to `Draft new codes from passages`. — "Drafting proposes new codes from selected passages."
3. [demo] Set `Backend` to `fake · offline demonstration`; leave `Model` on its task default. — "Use the offline fake backend to practice codebook development."
4. [demo] In `Source`, choose the source containing the sister response; set `Passages to send (1–20)` to `1`. — "Drafting uses passages from one source and the current code names."
5. [demo] Enter `Experiences of support` in `Focus (optional)`. — "An optional focus tells the proposal request what to consider."
6. [demo] Select the `Ask for proposals` submit button and wait for the result. — "The returned proposals still require a human decision."
7. Enter `researcher` in `Reviewer` and `Practice draft reviewed against the passage.` in `Decision note (optional)`. — "Your identity and decision note accompany the proposal decision."
8. [demo] Read the returned proposal's fields and reason. — "Read proposed definitions against the data rather than accepting them automatically."
9. [demo] Expand `Supporting passages` with its displayed count and inspect the excerpt. — "Supporting passages let you check the proposal against its evidence."
10. [demo] [zoom] Expand `Proposal provenance`; inspect `Backend / model`, `Mode` and `Based on codebook`. — "Proposal provenance records where the suggested change came from."
11. [demo] Select `Review and accept` on the new-code proposal. — "The code editor opens with values you can revise before accepting."
12. [demo] Inspect `Name`, `Definition`, `Include` and `Exclude` in the editor. — "Proposals can miss implicit meaning and blur boundaries between codes."
13. [demo] Inspect `Positive examples, one per line` and `Negative examples, one per line`. — "Examples in AI proposals are checked against the supplied passages."
14. [demo] Select `Accept into draft codebook`. — "Acceptance copies the confirmed values into the draft only."
15. [demo] Inspect the accepted code's origin caption and expand `Decided proposals` with its count. — "Proposals and your decisions remain part of the permanent record."
16. Select `Freeze codebook` when the draft is ready. — "Freezing the accepted draft stays a separate human decision."
17. [demo] Expand `Ask for proposals` if needed; set `Proposal type` to `Refine codes from review evidence`. — "Refining suggests revisions to existing code definitions and guidance."
18. [demo] Keep `Backend` at `fake · offline demonstration`; select `Support` under `Codes to refine (up to two)`. — "Refining uses coded and rejected passages with any review notes."
19. [demo] Select the `Ask for proposals` submit button; inspect the returned revision. — "A revision targets a code supplied in the request."
20. [demo] Compare `Current` and `Proposed` values and read the proposal's reason. — "Compare the suggested boundary with your intended meaning."
21. Enter `Keep the existing definition for this practice study.` in `Decision note (optional)`. — "Record why the proposed revision does not fit your judgment."
22. [demo] Select `Reject` on the refinement proposal. — "Rejection keeps the draft unchanged and records your decision."
23. Select `Find evidence in my reviews` under `Ask for proposals`. — "Evidence mining runs offline without an AI model."
24. Inspect the result and any returned proposals, allowing for no new proposals in this small study. — "Evidence proposals need qualifying review or coding patterns."
25. Expand `Decided proposals` and inspect the accepted and rejected decisions. — "Disclose AI-assisted codebook development in your methods."
